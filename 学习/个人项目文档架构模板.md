# 个人项目文档架构模板

> 在 Profit Calculator 验证、Conver System 复用的通用文档标准。个人项目文档不追求多，追求**每个文档只有一个角色、每条信息只在一处出现**。

## 一、文档角色表（单一事实来源分配）

| 文档 | 角色 | 只归它管的信息 |
|------|------|----------------|
| `CONSENSUS.md` | 需求 + 决策 | 产品决策、技术选型、规格定义。改设计先更新这里 |
| `TICKETS.md` / `TO-TICKETS.md` | **唯一待办事实来源** | 所有未完成/归档工单（完成记日期 + 提交哈希）。待办绝不落别处 |
| `DEV_LOG.md` | 已做 + 避坑 | 完成记录、bug 根因、进度。只记「已做」，不记待办 |
| `PROJECT_REFERENCE.md` | 项目介绍 | 一句话、关键决策、常碰坑点。不复制技术细节 |
| `README.md` | 用户视角 | 安装、使用、快速开始 |
| `CODE_WIKI.md` / `docs/` | 技术事实区 | 架构、API 契约、专项设计。改代码必须同步 |
| `CONTEXT.md`（可选） | 领域词汇 | 术语消歧、不变式、计算语义 |
| `docs/adr/` | 决策记录 | 影响面广/不可逆/多方案权衡的决策 |

## 二、三条铁律

1. **同一信息只允许存在于一个文档**，其他文档引用而非复制。凡在两处出现即漂移信号（测试数、方法签名、技术栈、路径是最常漂移的四类）。
2. **待办只进 TICKETS**，memory / DEV_LOG / 个人笔记不持待办。不落 TICKETS 就不算数。
3. **DEV_LOG 保持小**：`YYYY-MM-DD | <操作> | <描述>` 倒序 + 顶部滚动摘要。曾 615 行时每次会话读取耗 ~14K tokens——膨胀本身就是成本。

## 三、TICKETS 生命周期

📝 已录入 → 🔄 进行中（开始实现前认领）→ ✅/❌ 完成 → **移入归档表**并记完成日期 + 提交哈希。活跃表只保留未完成工单；新评审候选（含 `Worth exploring` / `Speculative`）立即录入。

## 四、防漂移机制（由简到繁）

1. **写入纪律**：写文档前自问「这条信息是不是已在别处写过？」（最便宜，够用很久）
2. **改代码后 grep 复核**：涉及测试数/方法名/API 路径/技术栈时，grep 相关文档残留
3. **审计执行前复核**：CR/审计产出是时间快照，执行前 `git grep` 当前代码，已就绪标「复核确认」而非重改（见 `[[审计快照过期需复核]]`）
4. **脚本自动化**（可选，F-01 已实践）：`doc_sync.py` 从代码生成测试数/方法表 + pre-commit 防漂移钩子
