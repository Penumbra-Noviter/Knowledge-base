## 二、做得好、值得固化的实践

### 2.1 流程：每类工作有明确产物，且单一事实来源

- **需求先拍板，代码后落**：grilling 追问 → 写进 CONSENSUS（共识文档）→ 拆成 TO-TICKETS 工单 → 逐张实现 → 完成归档。每个阶段都有可回溯的产物。
- **唯一待办事实来源**：`TO-TICKETS.md` 只放待办与归档，`DEV_LOG.md` 只记「已做」，memory 不存待办。彻底消灭「多个清单互相漂移」这个最常见的个人项目病灶。
- **工单生命周期入库**：每张工单完成时记日期 + 提交哈希，git 历史可完整回溯「谁在哪个提交实现了什么」。这是复盘时价值最高的习惯。
- **渐进式开发**：先 Tkinter 加功能验证需求，再迁移框架；MVP → 稳定性 → 体验 → 性能 的顺序贯穿始终。
- **评审驱动 × 原型驱动：方向归原型、质量归评审**：两者时间正交、天然咬合——评审驱动是**事后收敛**（实现 → 提交 → code-review → 分级入账 → 拍板，保证「做对了」）；原型驱动是**事前发散**（提问 → 一次性实现 → 亲手驱动 → 验证，回答「要不要做 / 长什么样」）。原型的收尾规则——验证过的决策落入主分支、原型代码进一次性分支——恰好就是评审循环的入口，所以结合不是硬凑。
  - **咬合形态**：评审循环是主流程，原型是上游「探针」，只在不确定性密度高的节点临时插入——评审拆出「实现方式有分歧」的工单、或新功能的状态机/数据模型在纸上推不动时，先插一个 `/prototype`（LOGIC 或 UI 分支）亲手推一遍再定方向，用完即走。
  - **选择矩阵**（经济判据：`决策的不可逆成本 × 影响面 > 原型成本` 才值得插原型）：

    | 节点特征 | 主导驱动 |
    |---|---|
    | 已有实现要改 / 质量把关 / 找缺陷 | 评审（保持现状） |
    | 还没代码，状态机 / API / 数据模型不确定 | 原型（LOGIC 分支） |
    | 多个 UI / 布局方案要选 | 原型（UI 分支，3 个结构化变体） |
    | 评审机会点实现方式有分歧 | 先 grilling 拍板，方向仍分歧再升原型 |
    | 连「要做什么」都不确定 | grilling（更上游，原型救不了没定义的问题） |

### 2.2 架构：深模块 + seam + 单向依赖，用评审驱动多轮收敛

- **`__all__` 定义协议面**：每个模块显式声明公开 API，天然逼着作者思考「暴露什么、藏什么」，也暴露浅模块（`DayRecord.total` 零引用、config 24 个孤立常量，都是协议面清扫时挖出来的）。
- **Seam 收敛跨对象私有访问**：`refresh_validity`、`fill_values`、`delete_requested.emit` 等公开 seam，让测试不再翻墙摸私有成员，UI 层与业务层边界干净。
- **依赖只能单向**：D-08 发现 `theme.py` 反向依赖业务层 `signals`（层反转），把信号枚举抽到零依赖叶子 `signals.py` 解决。**分层图的箭头必须画得出来，画不出来就是欠债**。
- **ADR 记录真决策**：满足「影响面广 / 不可逆 / 有多方案权衡」的决策才写 ADR。ADR-0001（序列化边界）同时解决了契约单点所有权 + 别名共享两个问题，是「一个决策消灭一类 bug」的范例。
- **评审候选分级入账**：Strong / Worth exploring / Speculative 全量记录，不拍的也写关闭理由（如 O-C2 多选日期范围——7 日架构是产品决策，改动会牵动表格/图表/summary 全局）。**关闭也是一种决策，留痕比沉默更有价值**。

### 2.3 测试：测真实路径 + 回归防复发 + 远离时间炸弹

- **测试即真实路径**：D-04 把「把 `refresh_validity()` 当测试后门」改为 QTest 真实事件链路（`keyClicks` 键入 → 去抖 → 校验 → 保存），保证被测试的代码就是用户点按钮会走的代码。这是本次质量提升最关键的一步。
- **回归测试防复发**：两个高危 bug 都用 AST 静态断言钉死——① 模块顶层禁止调 `get_color()`（C1 教训）；② `DATA_DIR.mkdir` 必须先于日志 handler（O-22 教训）。**测试不仅能验证行为，还能钉住「代码结构不许回退」**。
- **UI 烟测 offscreen 化**：`QT_QPA_PLATFORM=offscreen` 下跑 QApplication，CI 友好、可重复；夹具（`qapp`/`settings_guard`/`sample_window`）收敛到 conftest，不再每个测试文件重复造轮子。

### 2.4 文档：单一事实来源，分角色

| 文档 | 角色 | 关键约定 |
|---|---|---|
| `CODE_WIKI.md` | 技术细节唯一来源 | 方法表/依赖图/文件树，改代码必须同步 |
| `PROJECT_REFERENCE.md` | 项目介绍 | 只写背景/决策/坑点，技术细节指向 CODE_WIKI |
| `README.md` | 用户视角 | 使用/安装/打包 |
| `DEV_LOG.md` | 已做的事 + 避坑 | 滚动摘要 + 单行条目，控制体积 |
| `TO-TICKETS.md` | 待办事实来源 | 活跃表 + 归档表 + 提交哈希 |

最值钱的一条原则：**同一信息只允许存在于一个文档，其他文档引用而非复制**。O-19、D-08 的文档漂移修正都是在为「复制信息」还债。

### 2.5 交付：打包工程化 + 数据安全

- **spec 入库可复现**：`收益计算器.spec` 纳入版本控制，换机器可重建；瘦身配置内写注释说明依赖闭包校验法。
- **onedir + UPX 瘦身**：单文件 80MB 每次启动解压 181MB 是启动慢的根因，改 onedir 免解压 + excludes 剔 matplotlib/PIL + Qt 模块白名单 + UPX（117M→64M）。**每个打包决策都带着实测数据**（启动 1560ms vs 2~4s）。
- **运行态数据与程序隔离**：数据统一到 `Path.home()/收益计算器`，`data.json`/`settings.json` 出索引，杜绝「重建 dist 就丢用户数据」这类事故（O-20/O-21 踩过两次才定案）。
- **磁盘健壮性**：JSON 原子写入（tmp + replace）+ 滚动备份 + 损坏自愈 + 日志轮转，这是个人工具「数据不能丢」的底线。

### 2.6 决策文化：敢于关闭，先问「值不值」

- **YAGNI 主动关闭**：O-07 目标参考线（语义未定义）、E-01 保留天数可配置（用户不知道配置作用）、E-02 审计日志（覆盖写日志救不了撤销）、E-03 脚本化导出（无消费场景）。**功能不是越多越好，每个功能都要能回答「谁、在什么场景、用它解决什么」**。
- **grilling 拍板**：架构评审的 7 个候选用提问式访谈逐分支确认，避免盲目执行评审报告。

## 三、踩坑教训（重点复盘区）

以下按「付出代价大小」排序。每条都值得写进个人避坑清单。

### 3.1 测试夹具污染真实用户数据 ⚠️ 最严重

- **症状**：O-08/O-09 修复中发现，tests 里 `DataStore(tmp_path/data.json)` 未传 `backup_file`，默认指向**真实的** `data.json.bak*`——load 读真实备份、save 写回，测试跑一次就静默污染一份用户数据。
- **根因**：构造函数的默认参数恰好指向生产数据路径，测试没意识到「我写的是用户的备份文件」。
- **教训**：**测试环境必须与生产数据路径 100% 隔离**。凡是持久的读写路径，测试都要显式注入 tmp 路径，宁可啰嗦。
- **防复发**：`backup_file=tmp_path/...` 成为显式约定，写进 DEV_LOG 持久避坑清单。

### 3.2 固定日期测试 = 定时炸弹

- **症状**：C5 评审发现 `make_sample_data()` 硬编码 2026-07-20~27，而测试断言窗口是 [today-6, today]。**2026-08-03 起测试必失败**——一个平静的、当时全绿的测试，三天后必炸。
- **根因**：测试数据用绝对日期，生产逻辑用相对「今天」。
- **教训**：**所有涉及墙钟的测试数据必须相对 now 生成**（offsets 7/6/5/3/2/0）。绝对日期是时间耦合，等价于给未来埋雷。
- **加分项**：这是通过 `/code-review` 双轴审查（Spec + Standards）提前发现的，说明**提交前做代码评审的收益远大于事后 debug**。

### 3.3 主题色 import 期冻结——同一 bug 复发两次

- **症状**：模块顶层 `_SIGNAL_TO_COLOR` 在 import 期调 `get_color()`，颜色冻结成 light 主题。T-01 处理过一次，C1 又复发。
- **根因**：`get_color()` 的返回值依赖运行时主题状态，而模块导入发生在运行时状态建立之前。**把「运行时的值」在 import 期当常量固化**。
- **教训**：① 运行时状态绝不进模块顶层；② 同根 bug 复发说明**单靠修是堵不住的，必须上结构性防复发**——AST 静态检查顶层无 `get_color()` 调用。
- **通用化**：这其实是「初始化时序」类 bug 的代表（见 3.4），也是 Python 桌面/Web 框架常见陷阱。

### 3.4 空环境首启即崩（FileNotFoundError）

- **症状**：O-22 数据目录迁移后，exe 在空环境首次启动即崩：`main()` 先构造 RotatingFileHandler（打开 LOG_FILE），而 `DATA_DIR.mkdir` 只在迁移分支内执行，空启动提前返回时目录根本没建。
- **教训**：**「全新环境首次运行」是一条必须单独测试的路径**，尤其涉及目录/文件/初始化顺序时。回归测试用 AST 断言「mkdir 必须先于日志 handler」钉死顺序。
- **通用化**：初始化代码的顺序敏感性，是桌面应用打包后最常见的一类「开发环境正常、全新环境崩」。

### 3.5 打包覆盖丢数据——同一个坑踩了两次

- **症状**：`dist/` 重建是「整体覆盖」操作，O-20、O-21 两次踩「重建丢数据」，才最终催生 O-22 数据目录统一。
- **根因**：把「程序文件」和「用户数据」放在同一个目录。程序更新=覆盖目录=数据陪葬。
- **教训**：**运行态数据（数据文件、配置、日志）永远与程序安装目录分离**，这是桌面应用的铁律。一次迁移（复制非移动、幂等、失败仅 warning）+ 完整测试覆盖，把灾难变成一次升级。

### 3.6 文档漂移——反复发生、反复还债

- **症状**：O-19 修 CODE_WIKI 失同步、D-08 修 PROJECT_REFERENCE 测试数过时、DEV_LOG 精简时连带审计修复。测试数 187→204→217→221 每变一次，多个文档就要跟着改，漏一处就是漂移。
- **根因**：同一信息（测试数、方法签名、依赖版本）被复制到多个文档。
- **教训**：**信息要么是计算出来的（CI 自动生成），要么是单一来源 + 引用**。手工同步多个副本本质上不可能零漏。
- **量化代价**：DEV_LOG 615 行、每次会话读取耗 ~14K tokens——文档膨胀本身也是成本，精简为滚动摘要 + 单行条目（-61%）。

### 3.7 影子测试体系（verify_all.py，831 行）

- **症状**：C5 之前，UI 测试跑在一套独立的 `verify_all.py` 里，与 pytest 并行双轨。它有自己的夹具（tempfile）、自己的手动 backup/restore、自己的断言风格。删除时发现 tempfile 夹具目录残留 **31 个（168K）**。
- **根因**：测试能力是逐步长出来的，没及时并入标准体系，形成「两套真相」。
- **教训**：① **测试体系只能有一套**，能力并入 pytest 而不是另起炉灶；② **删除一次性工具时必须同步清理其运行态残留**（此后成为主动提醒约定）。
- **转折点**：C5 把 831 行并入 pytest（offscreen 烟测 13 项），同时把深度私有访问收敛为公开 seam——**这一迁移顺便提升了产品 API 质量**，是「测试重构反哺可测性」的正面案例。

### 3.8 依赖方向反转（层反转）

- **症状**：D-08 评审发现 `theme.py` 依赖 `calculator.py`（业务层），而业务层又用 theme 的信号——依赖图出现环/反向，破坏了「UI 依赖业务」的单向分层。
- **根因**：信号枚举定义在业务层，主题层为了映射颜色被迫 import 业务层。
- **教训**：**枚举/值对象这种零依赖领域概念，应放叶子模块**（`signals.py`），谁需要谁 import 叶子，而不是塞进高层让低层反向依赖。**分层依赖图的每个箭头都要是合法的**。

### 3.9 其他值得记的坑

| 坑 | 教训 |
|---|---|
| settings.json 测试污染（`win.close()` 写真实 SETTINGS_FILE） | 测试启动时重定向运行时文件到 tmp，finally 恢复——强杀也无污染窗口 |
| O-01~05 并行分支合并冲突（模块级 `logger` vs `_logger`） | 并行 worktree 前先约定全局命名；合并时把命名冲突当成必查项 |
| CSV 大额金额 K/M 缩写丢精度 | 先想清楚消费场景（Excel 人工查看 vs 机器读取），做决策要写取舍（O-16 选 A） |
| `isHidden()` 对未 show 顶层窗口恒 True | 依赖 Qt 状态查询前先验证它的语义，O-13 改用 `close()` 返回值断言 |
| E-02 审计日志「为撤销铺路」论据不成立 | 做功能前验证「它真能解决目标问题」——覆盖写日志只留「何时改」，救不了撤销，真撤销要历史快照 |
| 并行重构不同步 → 全量 pytest 全红（16 failed + 27 errors） | 大规模重构要分步提交、逐步验证，别攒到最后一口气 |

## 四、沉淀为可复用的工作方法

1. **评审驱动优化循环**：架构评审（找机会）→ 候选分级入账 → grilling 拍板 → 逐张实现（带测试）→ code-review 双轴审查 → 归档 + 哈希。这个闭环是 6 天里质量爬升的引擎，**比任何一次「大重构」都稳**。
2. **每个 bug 修复的三件套**：复现测试 → 修复 → 结构性防复发（AST 守卫/路径隔离/单一事实来源）。只修不复盘=下次换个马甲再来。
3. **一切「事实」单点化**：待办只进 TO-TICKETS，已做只进 DEV_LOG，技术细节只在 CODE_WIKI，数据路径只由 config 拥有。**凡是「在两个地方出现过的信息」都要警惕**。
4. **交付前先问数据安全**：程序目录和用户数据分离了吗？测试路径和生产路径隔离了吗？空环境能启动吗？这三问救过三次大事故。
5. **敢于关闭 + 关闭留痕**：YAGNI 不是偷懒，是「明确不做的功能比半做的好」。关闭理由写下来，未来重提时有据可依。

## 五、复盘反思：还能做得更好

- **文档同步自动化**：当前靠提交纪律手工同步测试数/签名，未来可尝试 CI 脚本从代码生成方法表与测试计数，把「漂移类」错误从根上消灭。
- **早期引入 code-review**：C5 时间耦合、D-08 层反转都是评审发现的。**评审前置到每个提交**比攒一批再审更省钱，可考虑 git pre-commit 钩子。
- **并行开发要有命名/接口先约**：O 系列并行分支的合并冲突本可避免，未来 worktree 并行前先定公共符号契约。
- **数据迁移策略**：O-22 选择了「复制非移动」以求稳妥，但留下了旧目录的清理债（E-04 至今仍在核对根目录 `data.json.bak*`）。**迁移要有明确的「何时清理源」时间点**，而不是无限期两套共存。
- **规模悖论提醒**：221 项测试对一个 10 模块的个人工具已经是偏重的投资，收益边界要清醒——**测试的每一行也是维护负债**，重点是覆盖真实路径和防复发，而不是堆数量。
