# 子代理空返回先辨层级再修机制

## 症状
- 子代理间歇性空返回：24/134 = 18%，主会话收到空结果（status=failed）
- 统一错误串：`Model returned no text, no tool calls, and no usage before completing the turn.`

## 根因
- 所有子代理跑在 `deepseek-v4-flash`（`agents-state.json` builtInModelOverrides 强制 general-purpose/Explore）+ custom openai-compatible **本地网关**（baseURL 为 null）
- 「no usage」= 响应连 usage 元数据都没有 → **网关/API 层返回空响应**，不是模型"无话可说"
- 与**并行峰值强相关**：24 个里 17 个集中在同一大批次（28 个 agent 并发）
- 与 **prompt 长度无关**（空返回平均 2464 字 vs 正常 2712 字）——排除"上下文过长"假说

## 代价
- 18% 子代理白跑，主会话需降级重调或人工处理；大批次项目半数 agent 空返回，任务进度整体受阻

## 教训
- 空返回**先看 error 串辨层级**：无 usage = 网关/API 层异常（查网关限流/超时、换模型）；有 usage 无内容 = 模型行为（改 prompt）
- 修 skill 前**先查已有规则是否覆盖**：project-kickoff 步骤 4 已有「异常退出 → 降级为新调用」，空返回本就在其覆盖内——再加独立重试规则就是 sediment（与 [[编排型skill子代理职责重叠先划作用域]] 同一教训）
- harness 无内置空响应重试配置（`cli/config.json` 仅 mcp/hooks）——重试靠编排层降级路径，不靠机制

## 防复发
- 空返回频率记入 DEV_LOG；降级重调后仍 >5% 高频 → 查本地网关（并行限流/超时），不是 skill 问题
- 大批次并行（>10 并发）前先小批量探路（先发 3 个验证网关健康）
