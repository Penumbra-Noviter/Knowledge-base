# 工作区解析回归让数据「看似消失」

## 症状
重新打包桌面端（侧car + Tauri 壳）后，用户报告"所有配置和会话记录都被清空了"。检查发现**数据完好**——用户真正的工作区 `D:\Desktop\tools\DeepTutor\data`（knowledge_bases/memory/partners/system/user）全在；桌面 exe 实际打开了**另一个空的**目录 `%APPDATA%\DeepTutor`（启动时才创建的空骨架），看起来像被清空。

## 根因
r3 提交把硬编码的自定义工作区常量 `CUSTOM_DEFAULT_WORKSPACE`（`D:\Desktop\tools\DeepTutor`，用户数据所在地）从"release 构建也生效"改为"仅 dev 构建生效"，理由是"与 docs/INSTALL.md 一致"。release 于是走平台标准目录 `%APPDATA%\DeepTutor`，而用户的全部配置/会话/伙伴数据都在自定义目录 → 桌面端指向空目录 → "数据消失"假象。

**本质**：改动涉及用户机器特定路径的 **release 行为**时，"文档一致性/通用性"不是充分理由——那是用户的偏好契约，改之前必须确认用户，不能单方面翻。

## 代价
- 用户恐慌（以为数据丢失），排查 + 修复 + 重新打包约 1 小时
- 用户明确说"这不是第一次"——同类工作区问题反复出现，说明缺结构性护栏

## 教训
1. 用户机器特定路径（默认工作区 / 数据目录）是**用户偏好契约**——为"标准/通用/文档一致性"改动它之前，必须确认用户，或提供不破坏用户数据的回退。
2. release 固化行为与用户自定义路径冲突时，**存在性检查 + 回退**是正确姿势：自定义目录存在就用它，不存在才回退平台标准目录——既尊重既有用户，又不破坏新装用户的通用性（两全，不需要二选一）。
3. 打包类交付冒烟必须用**用户的真实工作区并断言真实数据非空**（如 partners 列表非空），不能只用临时空目录——临时目录全绿 ≠ 用户数据可见。
