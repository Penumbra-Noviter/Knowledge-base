# 批次文档收尾须与审核窗口对齐

## 现象

td129-td132 批次（2026-09-23，ctrl）期末四轴审核给出 Recommended 2 条（S1 Standards + SP1 Spec，同源）：审核观察 `eb6de29..HEAD` 的 diff 无任何文档文件，且工作区 `PROJECT_REFERENCE.md` / `DEV_LOG.md` 尚无可本批记录 → 判「ctrl AGENTS.md『改行为/接口 → 更新 PROJECT_REFERENCE』与 spec §11 文档同步承诺未兑现」。

实际情形：TO-TICKETS 归档当时已在工作区（未提交），PROJECT_REFERENCE 与 DEV_LOG 是**审核返回之后**才写的。文档不缺失，只是**迟到于审核的快照窗口**。

## 根因

流程顺序错了：主会话把「文档收尾」放在了 code-review 之后（直觉上收尾是最后一步），而审核子智能体读取的是**派发时刻的磁盘快照**——此时收尾文档尚未落盘。审核无法区分「从未写」与「还没写」，只能按缺口计。

## 处置

收尾 docs commit（`ed1da80`）落盘后缺口自然闭环，Recommended 消失；但审核报告已产生一轮噪音，且审核者可能据此降低后续判定权重（狼来了效应）。

## 复用建议

- 批次文档收尾（TO-TICKETS 归档 / TECH_DEBT 处置 / PROJECT_REFERENCE 行为描述 / DEV_LOG 批次节）应在**波末合并完成后、期末 code-review 派发前**完成并 commit。
- 需要审核结论才能写的部分（如期末四轴结论行、审核产出的新债编号）单独回填一次小 commit，不要因此把整批文档推后。
- 判据：派发期末审核前，先确认工作区里四件套文档已含本批事实——否则审核必然再报一次同样的缺口。
