# 配置文件白名单归一化会静默删除外来键

## 症状

桌面壳每次关闭都弹「Close behavior」确认框，用户明明选过「最小化到托盘」。排查发现：壳把 `close_behavior` 键写进 `data/user/settings/system.json`，下次关闭读不到——每次都被当成「首次关闭」。

## 根因

`RuntimeSettingsService._load_or_create` 的流程是：读文件 → 用 `{**defaults, **loaded}` 合并 → 过白名单归一化函数（只输出已知键）→ **发现归一化结果 ≠ 磁盘内容就原子重写文件**。壳写入的 `close_behavior` 不在 Python 的白名单里，后端任何一次 `load_system()`（启动、设置读取）都会把整个文件重写一遍，外来键被静默丢掉。错误被 `let _ = write_close_behavior(...)` 吞掉、`_load_or_create` 无日志，全程无痕迹。

## 代价

- 一个行为偏好「永远记不住」，每次关闭弹窗
- 根因排查跨越壳（Rust）与后端（Python）两侧，读了两套代码才定位到「壳写键 + Python 归一化重写」的跨进程交互

## 教训

**共享 JSON 设置文件前先划分所有权：每个进程只写自己拥有的文件**。壳/外部进程的自有状态用独立文件（`desktop.json`），不要借道归配置服务 schema 管理的文件（`system.json`）；改配置服务的白名单去「宽容」外来键是次优解——下次白名单变动还会再删一次。

## 防复发

- 外部进程（壳、sidecar、脚本）需要持久化状态时，新建 `data/user/settings/` 下的专属文件，并确认配置服务永不 touch 它
- 配置服务侧：`_load_or_create` 的「归一化 ≠ 磁盘即重写」语义对未知键要保留（防 schema 漂移），所以所有权隔离是正道而非改它
- 写入方对 `Result` 丢弃前先想「读不回怎么办」——静默失败 = 下一次诡异行为
- [x] 已落实？（DeepTutor：偏好已迁 `desktop.json`，`read_close_behavior` 回读旧键兼容）
