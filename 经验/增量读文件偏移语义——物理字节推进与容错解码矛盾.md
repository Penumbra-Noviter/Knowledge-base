# 增量读文件偏移语义——物理字节推进与容错解码矛盾

## 症状
Windows 下 GUI 轮询增量读子进程输出文件（`read_output_chunk(path, offset)`）：offset 按「解码后文本的字节数 + 换行数」推进（`len(text.encode()) + text.count("\n")`）。两类输入下出错：

- 块边界落在多字节 UTF-8 字符中间：文件内容 `中A`（2 字节 `E4 B8 AD` + `41`），首块读 2 字节 `E4 B8` → 按公式推进 3（`len("\uFFFD")` 也算 1 字节 + 2 原始字节 = 3），第三字节 `AD` 永久丢失，拼接 `<U+FFFD>A` 而非 `中A`；
- 文件含非法 UTF-8 字节（`errors="replace"` 容错路径）：22 字节文件（含 `b"\xff\xfe"`）按公式推进后漂移 6 字节，第二次读取返回空，尾部输出静默丢失。

旧实现（文本模式读 + `tell()`）精确无此漂移——**该缺陷是本实现引入的契约级回归**。

## 根因
两个空间的字节数不一致：`offset` 语义是**物理字节**（二进制读），但调用方从**解码后文本**推导推进量。`errors="replace"` 把非法序列替换为 U+FFFD（1 字符但可多字节），`len(text.encode())` 已不是物理消耗字节数；块边界切在多字节字符中间时，已读文本的编码长度 < 物理消耗长度，下一块从错误偏移续读，残留字节丢失。

## 代价
- 期末 Falsify 探针实测暴露（2 字节 `E4 B8` 推进 3 丢 `AD`；非法字节文件漂移 6 字节）；
- 波末 + 期末双审核累计 4+3 条 findings，落 TD-110/TD-111 候选区（推进公式脆弱性 + 切分边界三类缺陷 + marker 子串误判）；
- 当前唯一调用方（ElevatedCapture）受写侧「逐行转发 + marker 单次 flush」保护不可达，未酿成线上事故——但 `read_output_chunk` 是公开 API，契约未声明前置约束，任何新调用方首用即踩。

## 教训
公开的增量读 API 必须自己管理偏移——首选签名 `(path, offset) -> (text, done, new_offset)`（new_offset 由读取方从**原始字节**算出）；或保持文本模式读 + `tell()`（偏移语义由 IO 层管理）。**绝不让调用方从解码后文本推导物理推进量**——decode 前后的字节空间不可互换。
