# 中间转换层转圈丢字段——全量产出消费子集

## 症状
`CharacterDraft.fromParseResult`（16 字段草稿工厂）产出全字段草稿后，向导 `_applyParseResult` 只拷 8 个表单字段进表单，`save()` 又**重建** Companion——解析出的 `postHistoryInstructions` 从未落库。字段 docstring 却写「postHistoryInstructions 经 fromParseResult 保留于草稿可落库」（声称保留，实际丢弃）。

## 根因
「A → 中间 DTO → B」转圈路径里，中间层按全量契约产出，消费方只取子集后**丢弃中间产物重建 B**——未取字段随中间产物一起消失。转圈路径让「谁消费了什么」不透明：写工厂的人以为保留，写 save 的人只看到表单字段。误导注释把「以为对」固化成了文档事实。

## 代价
chat_service 对话时消费该字段（系统提示注入）——丢失是真实功能缺口；排查从注释到实现花了整轮 grilling 拍板（解耦 + 修复 vs 保真）。

## 教训
- 转换链若存在「全量 → 子集」的中间层，**子集之外的字段必须显式处置**（要么消费方接管并落库，要么删中间层直拷）；
- 注释声称的行为必须有代码佐证——「保留于草稿」而草稿被丢弃 = 文档说谎；
- 收敛手段：删中间层（直拷），需要保留的字段显式接管。

## 防复发
- [x] DTO 转圈路径 review 时逐个核对中间层字段的去向（消费方全取？丢弃？）；
- [x] 声称「保留/落库」的注释 grep 到实际写库点验证；
- [x] 新增落库断言锁「解析字段随保存落库」的端到端行为。
