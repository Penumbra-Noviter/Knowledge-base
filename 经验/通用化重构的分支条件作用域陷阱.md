# 通用化重构的分支条件作用域陷阱

## 症状

T-441 把 report.py 的 `_render_reviews` 三路 if 分派（review/nonce/evasion 各写
一段渲染）改通用循环时，主会话共识 D11 把旧实现 evasion 分支内的 note 兜底
（`if fired: ... elif block.note:`）字面泛化成 `elif block.note:` 全通道通用——
实测 test_report.py 3 条字节断言红：review/nonce 通道的 note 被追加进展示行，
而旧渲染从不显示（`_deep_report_with_reviews` 的 review 有 note「未发现与诚实
零模型的显著矛盾」、nonce 有 note「非ce 回显率 87.5%」，断言锁定不显示）。

## 根因

三路分派里「每通道渲染参数行」是**形状知识**（α/p/回显率/信号数——泛化正确），
但「note 兜底」是 **evasion 通道的分支内特有条件**（有 signals 明细能力的通道
无信号时用 note 补充）。两者同在一个 if 分支里，泛化时被当作同一种知识一起
提升为通用条件。字节保持断言先红——它恰好是「泛化是否正确」的试金石。

## 代价

若按 D11 字面落地：review/nonce 的 HTML 复核行多出 note 内容，用户可见输出
变化 + 3 条断言要改（字节保持硬验收破）。实现代理按裁决协议停下上报，主会话
采纳 `_HAS_SIGNALS` 注册表驱动守卫（`elif block.note and block.key in _HAS_SIGNALS:`，
`_HAS_SIGNALS` 由注册表 `fields` 含 "signals" 的通道推导）——字节保持 + 数据驱动
双满足，122 测试全绿。

## 教训

通用化重构（三路分派 → 循环/注册表）时，对原分支内每个条件做**作用域分类**：
① 属于「形状」（每通道各异的字段/模板）→ 进注册表数据驱动；② 属于「通用逻辑」
（所有通道一致）→ 无条件通用化；③ **分支内特有条件**（只在一个分支出现、
语义绑定该分支能力）→ 不能无条件泛化，需显式决定：注册化（作为形状的一部分
声明，如「有 signals 字段的通道启用 note 兜底」）或保留分支。判断标准：
「如果未来加一个没有该能力的新通道，这个条件应该怎么表现」——答案不是默认
值就是注册表声明。

## 防复发

- 泛化前逐条枚举原分支条件，标注 ①②③ 分类；③ 类条件不得写进共识/工单的
  「通用」字面（本批 D11 的 `elif block.note:` 就是③被写成通用）
- 字节保持断言是泛化试金石：渲染/输出重构必须保留逐字节断言，红了先怀疑
  「条件作用域错了」而非改断言
- 形状注册表优先按「能力」推导守卫（fields 含 X）而非按 key 字符串硬编码
