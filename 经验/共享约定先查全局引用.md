# 共享约定先查全局引用

## 症状
- code-review 的「轴数」约定散落在四处：code-review skill、code-review 子智能体、implement 子智能体、project-kickoff 编排文档。
- P0 把审核升级为三轴（Standards + Spec + Falsify）时只改了 kickoff 编排描述，implement.md 的自查仍是「双轴自审」、code-review.md description 仍是「双轴 + 并加 Falsify」。
- P3 统一时全局 grep 才发现残留 5 处「双轴/两轴」——体系描述前后不一致。

## 根因
- 一个跨文件共享的约定没有**单一事实来源**；改一处时只搜了「当前文件」的心理范围，没有先全局检索该术语/规则的所有出现位置。

## 代价
- 三处文件描述不一致持续两个批次（P0→P3），额外一轮 P3 返工；
- 更糟的是主智能体按过时描述派发（implement 自查少一轴，Falsify 在提交前缺失）。

## 教训
- 改任何跨文件共享的术语/规则/轴数前，先 `grep -rn <术语>` 全仓列出所有出现位置，逐个核对；或把共享约定收敛到唯一权威文件，其余文件只引用。

## 防复发
- 编辑跨文件约定前强制全局 grep（P4 已形成习惯：编辑前先 grep 目标术语及其旧词）；
- 新约定落盘时声明「权威文件」（如审核轴数以 code-review 子智能体为准，其余引用之）。
