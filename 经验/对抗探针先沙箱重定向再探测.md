# 对抗探针先沙箱重定向再探测

## 症状

本批次两次实锤：Falsify 子代理首轮把探针脚本写进了真实 plugins/（靠固定名自掩蔽未被发现，后用 uuid 名复现）；期末定向复审代理首轮未重定向模块全局常量，import 产品模块喂敌意输入时**真的清空了主仓库 registry.json** 的 clean_cache 条目（当场 git restore 抢救）。

## 根因

探针目标是"让代码在敌意输入下暴露失败路径"，而产品代码里的写路径常量（PLUGINS_DIR/REGISTRY_PATH）指向真实仓库——不重定向就等于拿生产数据当靶场。"只在临时目录放恶意 JSON"不够：被测函数内部会自己走向真实路径。

## 代价

两次主仓库污染（均恢复）+ 复审返工一轮；若无 git 干净基线与事后核验就是数据事故。

## 教训

Falsify/评审子代理的探针规范顺序固定为：先 autouse 式重定向全部写路径常量到临时沙箱 → 再 import 产品模块 → 喂敌意输入；结束贴 `git status --short` 作为零污染证据。主会话对"自称已清理"必须用磁盘事实复核（本次核验发现恢复有效）。
