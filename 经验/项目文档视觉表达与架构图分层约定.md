# 项目文档视觉表达与架构图分层约定

## 症状
写项目文档（README / PROJECT_REFERENCE / CODE_WIKI）时，agent 倾向只吐大段文字，缺视觉辅助，读者抓不住结构和关系。反过来，若把独立 HTML 架构图（如 Archify 产物）当作权威架构说明，图不会随代码自动更新，`doc_sync.py` 也校验不到，制造第二个漂移源。

## 根因
视觉表达缺「场景→形式」的先验清单，agent 不知道该用什么形式；架构图未分层——把「示意附件」和「权威事实源」混为一谈，破坏了 CODE_WIKI 的单一权威源。

## 代价
文档难读，结构关系靠文字硬描述；架构图过期后 `doc_sync` 抓不到，权威性被悄悄架空。

## 教训
视觉表达遵循「最小视图 + 图分层」：权威架构事实留在 Markdown（文字树形 / Mermaid，可被机械校验），精美交互图（Archify）只当「点开看的示意附件」，永远不进 `doc_sync` 校验、不当唯一真相源。

## 防复发
### show-me 视觉表达清单（常驻，写文档时用）
| 场景 | 形式 |
|---|---|
| 逻辑 / 算法 | 伪代码 |
| 运行时控制流 | 调用树 |
| UI 结构 | 组件树（含 state / 模块边界） |
| 文件职责 / 大重构 | 浅文件树 |
| 组件交互 / 数据流 | Mermaid |
| 「什么变了」 | diff（组件 / 文件布局 / 调用栈 / 状态） |
| 大部分是新的 | 完整代码块 |
| 视觉 UI / 密集概念 | 聚焦 HTML + open |

原则：最小视图讲清关键点，别淹没读者。

### Archify 分层接法（低频专用，别常驻）
| 文档层 | 用什么 |
|---|---|
| CODE_WIKI `§文件结构` | show-me 浅文件树（文字树形，doc_sync 可校验） |
| CODE_WIKI 模块依赖 / 调用 | Mermaid 内联 |
| README / PROJECT_REFERENCE 顶部全景图 | Archify HTML 附件（示意，不进校验） |
| ADR 的 Before/After | show-me diff 形式 |

### 接入决策
- show-me：直接接，常驻（纯 prompt，零成本）。
- Archify：接，放「低频专用工具」区，触发条件 =「要给项目产出一张可交付的架构图」。
- 红线：Archify 的 HTML 不纳入 `doc_sync` 校验，明确是示意附件，权威架构事实仍在 Markdown。
