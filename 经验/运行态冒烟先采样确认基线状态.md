# 运行态冒烟先采样确认基线状态——命名与视觉描述是假设，像素采样才是证据

## 症状
F-7/F-8/F-9 批次冒烟：应用启动后把第一张截图命名为 `smoke-settings-dark.png`（假设「应用默认深色」），随后切浅色截图为 `smoke-settings-light.png`，计划以「深色基准 vs 浅色切换后」对比验证 F-7 浅色对比度。事后像素采样发现**两张截图背景都是 #F0ECE5**（浅色 page token 精确值）——应用持久化主题为浅色（前会话收尾态），启动即浅色，所谓「深色基准」不存在。

## 根因
两层叠加：① 文件名编码了**假设**（"dark"——默认深色的预期）而非事实；② 先入为主的基线预期让后续视觉描述也被合理化解释——vision.js 分析图中说「背景米白、非深色」时，第一反应是模型描述不准，而非怀疑自己的基线假设。缺一个**先于结论的确定性探针**。

## 代价
一次无效「深色基准」采集 + 一轮事后返工（重新切深色、重截图、重对比）；若未发现，冒烟证据会带着错误的基线标签归档（好在像素采样在归档前兜住）。

## 教训
**运行态验证的第一步是先采样确认基线状态，再下结论**——主题/语言/登录态等可程序化探针的状态，「截图+文件命名」与「vision 描述」都不是确定性证据：文件名编码假设、视觉模型描述可模糊可误判；像素采样（背景色 == 已知 token 精确值，如 #F0ECE5/#171512）或 UI 树读取才是。任何「切换前 vs 切换后」对比，两态都要有独立确认，不许用第一态当免检基准。
