# 流程 skill 英文化不省时间：先拆假设再动

## 现象

提议：实际运行中（子智能体 prompt/编排文件/spec）纯英文最节省时间，只在项目端（代码/文档）和交付端（用户汇报）用中文，兼容性更好。

## 假设拆解

1. **时间**：墙钟时长大部分是网关等待（M 批次实证：极端会话 96%），token/请求数才是关键变量——prompt 语言对墙钟影响可忽略；token 数中文不劣（信息密度高，"波末文件范围核验"8 字 ≈ 8-12 token 与英文同义表述相当）；deepseek 系中文语料占比高，中文 prompt 推理质量通常不低于英文。
2. **兼容性**：收益低频——模型（builtInModelOverrides 强制）与网关固定时，"换模型/换网关/跨工具粘贴"场景不出现；风险真实——凝练术语翻译有语义损失（"已定前提不得重开""零冲突≠零丢失"），validate_skills.py 软检查依赖中文模式（计数式表述正则），38KB 大改有回归成本。
3. **混用**："中文正文 + 英文技术术语"（worktree/spike/Falsify/token）是合理混合（术语可移植），不是混乱混用；语言分工边界已存在：分支/commit/文件名英文（`kickoff/<编号>-<slug>`、`feat:`），交互中文。

## 决策

维持现状（中文正文 + 英文术语）。若怀疑"英文更快"，先做同批 A/B 小实验证伪（一半中文 prompt 一半英文，对比墙钟/空返回率/首测通过率），先验（M 批次数据）指向无显著差异。

## 可迁移

语言/效率类假设先拆**墙钟构成**（token/请求数 vs 语言）再拆**收益场景**（低频 vs 高频），不预埋；真实事故（如工具对中文路径/输出的处理问题，属编码而非语言）再针对痛点动。
