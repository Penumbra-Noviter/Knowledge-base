# 占位符计数器失同步——Falsify 须覆盖防御机制自身状态机

## 症状
markdown 代码块占位符原子化（TD-38）实现后，自审「碰撞循环实测兜底」声称安全，单块场景全绿；期末四轴 Falsify 构造**多代码块 + 用户内容含 `\u0000MDCB<n>\u0000` 形文本**时，首块内容被第二块覆盖丢失（SECOND 双份、FIRST 消失），已提交套件对该路径零覆盖。

## 根因
`createCodeBlockToken` 的 do-while 碰撞循环**内部消耗多个序号**（如 0、1 后返回 MDCB1），但调用方只做一次 `tokenId++`——内外计数器脱钩。第二个块从 tokenId=1 起检发现 MDCB1「未被占用」（原串只有用户字面 MDCB0），复用 MDCB1 → Map.set 覆盖首条记录 → 还原循环把两处占位符都替换成第二块 HTML。取号逻辑拆在两处（Locality 违约）是失同步温床。

## 代价
- 期末审核 1 阻断 → 派回 Implement 修复 + 复审（5 防复发用例转正 + 取号收进单一职责）
- 若未在期末抓到：用户内容含 NUL 形文本（不可键盘输入，真实可达性极低）且 ≥2 代码块时静默丢内容——契约失效但无崩溃信号

## 教训
**防御机制的对抗测试必须覆盖机制自身状态机，而非只测单实例输出正确性**——「碰撞循环兜底」的自我声明只验证了「跳号」单点，未验证「跳号后计数器推进与内部消耗同步」这条跨实例不变量。凡是有序占位符/序号/id 分配器，Falsify 必测：多实例交错 + 用户内容占用中间序号 + 三实例链，断言「每块恰出现一次、无泄漏」。
