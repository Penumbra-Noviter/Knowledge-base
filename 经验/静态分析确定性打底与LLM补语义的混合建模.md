# 静态分析确定性打底与 LLM 补语义的混合建模

## 症状
让 LLM 直接读大代码库做「理解」，产出不稳定：同一段代码两次分析可能给出不同摘要，结构关系（谁 import 谁、谁调用谁）可能编错，且全量读源码 token 消耗巨大。反过来，纯静态分析（AST/LSP）只能给出结构事实，无法回答「这个文件是干嘛的」「业务上属于哪一层」。

## 根因
结构事实（import/export/函数类定义/调用点/继承）是确定性的，属于语法层面，解析器能做到「同输入同输出」；语义（摘要、标签、架构分层、业务领域）需要自然语言归纳，是 LLM 的强项。把两类任务塞给同一层，要么让结构不可复现，要么让语义不准确。

## 代价
Understand-Anything 的做法是 tree-sitter 预解析出 importMap 和结构事实，再喂给 LLM 只做语义归纳。若反着来（LLM 全包），大型仓库一次全量分析可消耗数十万 token，且每次重跑结果漂移。

## 教训
代码库建模按「确定性打底、语义补高层」分层：结构事实交给解析器（tree-sitter / LSP），LLM 只负责解析器做不了的意图归纳，两层边界清晰、可复现、可增量。

## 防复发
- [ ] 落地代码理解工具时，先确定「哪些事实是确定性的」清单（定义/引用/调用/继承），全部走解析器，不交给 LLM 猜
- [ ] LLM 的输入始终携带已解析的结构事实，禁止它从源码重新推导结构
- [ ] 语义层产物（摘要/分层）标注「LLM 生成、可能漂移」，结构层产物标注「确定性、可复现」
