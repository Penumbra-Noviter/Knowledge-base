# 枚举/分类设计要用异质样本证伪（同质样本只确认偏差）

## 症状
- 从 AI自动获客 一个项目提炼的「正交面」目录（功能/UI/责任/安全/发布 五面），用 conver、hanhua 两个对照项目验证——**全过**，看起来目录完备。
- 换成与来源**异质**的样本（开源库、移动 App、SaaS）一推，立刻逼出五个缺漏面：文档、兼容/维护、商店审核、运维/可观测、成本/计费。

## 根因
- conver/hanhua 与 AI自动获客 是**同质样本**（都是个人开发者的桌面应用），它们只会覆盖同一类项目的面，「全过」只是确认偏差，不构成完备性证据。
- 枚举/分类设计天然倾向「样本内封闭」：你能想到的项，都是样本里的项。打破它必须引入**样本外的**输入。

## 代价
- 只用同质样本确认，会交付一个「看似完备、实则过拟合单类项目」的目录；用到别的项目类型（库/App/SaaS）才发现缺面，而缺的恰是那些项目最要命的面。

## 教训
- **枚举/分类设计必须用「与提炼来源异质」的样本证伪**：同质样本（哪怕 3 个）只能确认，不能证伪；异质样本（哪怕 1 个）才逼出缺漏。
- 判定「异质」的口径：与来源在**根驱动**上不同（本例：交付意图 / 业务性质 / 项目类型）。
- 同质样本的「全过」不得作为完备性证据写进结论。

## 防复发
- [ ] 任何枚举/分类交付前，显式列一组「异质证伪样本」并跑一遍：缺漏项要么补进目录，要么显式声明「本枚举只覆盖 X 类项目」。
- [ ] 目录类产出附一句边界声明（覆盖哪些项目类型、哪些不覆盖）。
