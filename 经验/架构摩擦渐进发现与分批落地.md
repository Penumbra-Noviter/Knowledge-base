# 架构摩擦渐进发现与分批落地——多轮轻量评审替代一次性大重构

## 症状
系统 Phase 1-5 快速迭代后存在大量架构摩擦（路由层过厚、service 层职责混杂、前端 app.js 膨胀到 1380 行、死代码、文档漂移）。如果一次性大重构，影响面太大、风险太高、难以验证。

## 根因
快速迭代积累了技术债，但大重构在一个仓库中难以安全执行——测试覆盖可能不完整、行为变更难以逐项验证、并行工作流冲突。

## 代价
三轮架构评审（▲11 候选 → ▲5 候选 → ▲3 候选），每轮 1-2 天，逐步落地。每轮含：评审 → 分批落地（每批经独立测试验证）→ 归档。总耗时约 5 天，但零回滚、零行为破坏。

## 教训
**架构改进的推荐模式是多轮「评审 → 发现 → 分批落地」的轻量循环**，而非一次性"架构重构周"：

1. **评审阶段**：跑 code-review 工具，按维度列出候选改进项，不评优先级，不承诺落地
2. **分批阶段**：每批选 3-5 个相互独立的候选，并行或串行落地，各批独立测试验证
3. **归档阶段**：每批完成后更新 TICKETS 归档 + DEV_LOG，确保 git 历史可追溯每项变更

**关键原则**：
- 每批候选必须**行为保持**（不改变功能语义），否则属于新功能不是重构
- 每批落地后测试全绿是硬性条件
- 候选之间有依赖的放在同一批，无依赖的可以并行
- 落地一批就归档一批，不留"半重构"状态

## 防复发（惯例：开工预检时对照执行，无需勾选；动作项见条目内去向）
- [x] 三轮架构评审 11+5+3 候选全部落地，零回滚
- 新项目也采用此模式，不设"重构周"
