# 并行 worktree 合并「零冲突」≠ 零丢失——共享文件被静默覆盖

## 症状
共享 Modal 组件重构（`540d5bd`，6 页改造）被随后合入的 DAO/Repository 大合并（`d882679`/`0aa4592`）**整体覆盖**，审查/运行时才发现 Modal 改动不见了。

## 根因
两个并行分支各自从旧基线出发改同一批共享文件（`utils.js`、`style.css`、6 个页面）。后合入方改动量大，两边没改到同一行 → git 判定「无冲突」→ 一方的改动被**旧基线内容**覆盖。git 只检测行级冲突，检测不了「语义上的覆盖」。

## 代价
8 文件 +339/-520 的 fixup 返工提交（`cf6ce27`「fixup: 恢复 Modal 组件改动（被 DAO 合并覆盖）」）；事故从未进入 DEV_LOG，蒸馏无从取材。

## 教训
**worktree 并行合并且「零冲突」时，凡涉及共享文件（工具函数、共享组件、公共样式），必须把该文件列为合并后必查项**；合并验证不只查「有没有冲突」，要查「改动是否还在」。修复类事故必须带「根因一句话」进 DEV_LOG，否则复盘的源头是断的。

## 防复发（惯例：开工预检时对照执行，无需勾选；动作项见条目内去向）
- 并行分支开工前声明共享文件清单（类似[[测试与架构高频小坑汇总]]的并行命名契约）
- 合并后对共享文件做 diff 抽查，确认双方改动都在
- 事故性修复进 DEV_LOG 必须写根因
