# 聚合语义字段跨模块复用须核对语义（filled 含幂等匹配误当真写入信号）

## 症状

SIM-API-1 观察者熔断计数用 `filled > 0` 判定「宿主真改了游戏配置」。filled 的实际语义是「字段已处于目标值（含本次写入**与幂等匹配**）」——值已匹配时同样计入。后果：配置控件自身的良性属性翻转（setAttribute class/disabled）或分散合法重建连续 3 次后，**熔断误触发**，自动同步被静默压制（面板保持游戏默认值，无任何 UI 指示，仅手动「重新同步」可救），ADR-0001「重建配置控件后重新同步」承诺静默失效。

## 根因

两个模块对同一字段的语义理解漂移（Divergent Change 边缘）：

- key-injector 定义 filled = 已处于目标值（聚合语义，含幂等匹配——这是 SIM-API-1 幂等写回环守卫的刻意设计）；
- simulator-view 消费时解读为「本次实际写入」（真写入信号）。

聚合语义字段在定义处有 docstring 说明，但消费方**默认按名字直觉解读**（filled ≈ 写入过），不核对定义——语义漂移在单测里不可见（测试夹具构造的都是真写入场景），只有构造「幂等匹配」输入的 Falsify 实证能暴露。

## 修复

key-injector 返回增 `written` 字段（本次真写入并派发事件的字段，filled 的子集），熔断/反馈类消费方改用 written 判定「宿主真改了游戏配置」；filled 语义不变（既有消费方——按钮反馈、幂等守卫——不受影响）。顺带收窄 attributeFilter（只监听票面目标属性 value/hidden），消除良性属性翻转的触发面。

## 教训

1. **聚合语义字段跨模块复用前，消费方须核对定义层精确语义**——尤其「计数/阈值/反馈类逻辑」，一个字段名两种解读必然出错；宁可加一个精确语义字段（written）也不复用语义更宽的字段。
2. **Falsify 实证是语义漂移的暴露器**：构造「值已匹配」的幂等输入（控件重建后保持目标值）打熔断逻辑，误触发立刻现形；happy path 单测永远测不到。
3. **熔断/节流类防御机制的触发信号要用「真发生」而非「状态达成」**——病理循环的判别依据是「宿主真的写了」（游戏在重置），不是「字段处于目标态」。

## 可复用场景

任何「聚合/状态类返回值被下游计数或触发阈值」的跨模块消费（如进度聚合、去重计数、限流信号）。加字段成本远低于语义漂移的排查成本。
