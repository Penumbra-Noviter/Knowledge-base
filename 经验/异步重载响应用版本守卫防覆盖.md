# 异步重载响应用版本守卫防覆盖——后返回的响应不覆盖先写入的数据

## 症状
P6.5 多 tab 中,流式对话完成后 `finalizeStream` 调 `messages.list` 重载消息列表。list 请求在途期间用户连发新消息(新 user 消息已入 per-tab 缓存),旧 list 响应返回后 `updateTab(全量替换)` 把新 user 消息从缓存和 DOM 同时抹掉——`isActiveStream` 同 tab 为 true 时还把陈旧快照渲染上屏,新流 onToken 用 `filter(!streaming)` 重建后该消息永久不可见(数据在服务端,重新激活才恢复)。

## 根因
「重载响应」与「本地增量写入」两个异步源竞争同一状态:重载发起的时刻捕获了旧快照,返回后无条件整体替换,把发起之后、返回之前发生的本地变更覆盖掉。这是「后返回的响应覆盖先写入的数据」——异步 UI 中响应乱序/在途变更的经典竞态,本项目 spec 明确承诺消除此竞态类,却在同 tab 连发场景残留。

## 教训
**异步重载的响应要带版本守卫**:重载发起前捕获当前数据版本(此处为 `messages.length`——缓存长度单调非减,早发 list 一旦有后续 append 必 stale),响应返回后**仅当当前版本 === 捕获版本**才整体替换,否则丢弃(由后续重载或本地增量承接)。配套:终态写回后立即刷新依赖状态的 UI(发送按钮),消除「状态已变、UI 还显示旧态」的 UX 窗口。

```js
// 重载前
const revision = getTab(convId)?.messages.length;
const msgs = await messages.list(convId);
// 返回后
if (getTab(convId)?.messages.length !== revision) return; // 期间有新数据,丢弃陈旧快照
updateTab(convId, { messages: msgs });
```

长度守卫的成立条件:数据变更只增不减(append-only);若有删除/重排,改用显式版本号(计数器/时间戳)。另一处同型(非流式路径)注释明示「同型守卫」,因分支语义有实质差异(陈旧分支仅流式有 settle)未强行抽 helper——重复守卫且形态略异时,先判断差异是否实质,不机械 DRY。

## 补充：异步插入/删除场景下「索引会漂移，对象引用永不移位」

版本守卫（length 比较）防的是**追加型**漂移（连发使长度变化）。但插入型操作会移动后续元素的**索引**——P6.5 三连发 + list 全失败场景实测：前流失败按「发起时刻尾位置」写回时，数组收缩（并发流 token filter 掉旧占位）+ 插入顺移（aA 插到 u1 后使 u2 索引 +1）导致位置完全错乱（消息插进 user 中间、streaming 残留）。

**用对象引用代替索引定位**：捕获「本流 user 消息对象」而非其索引，写回时 `next.indexOf(anchor)` 现查位置——user 消息本身不被删除（append-only），引用永远有效；任何插入/删除造成的索引漂移都不影响定位。最终三连发场景 `[u1, aA, u2, aB, u3, aC]` 零丢失零残留，与理论顺序完全一致（commit 1f2fdcc 前为索引方案的失败现场）。

教训：**异步状态合并的锚点用「对象引用 + indexOf」而非「数字索引」**；数字索引只在纯 append-only 且无插入的模型下安全。
