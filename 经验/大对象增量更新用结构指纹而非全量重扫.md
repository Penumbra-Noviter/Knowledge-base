# 大对象增量更新用结构指纹而非全量重扫

## 症状
为整个代码库生成图谱/索引后，每次代码提交都要重新全量分析，token/时间成本与首次分析相同，导致图谱维护成本高到没人愿意保持新鲜，最终图谱过期作废。

## 根因
没有一种廉价的「变更检测」手段。用 git diff 只能拿到文件级变更，但「结构是否真的变了」还需要逐文件重新解析；如果干脆全量重扫，就失去了增量意义。

## 代价
Understand-Anything 的解法：用 tree-sitter 为每个源文件生成「结构指纹」，commit 时对比指纹，只有指纹变化的文件才重新分析。若无此机制，一次增量本可只花变更文件的成本，却要付全量成本。

## 教训
大对象（图谱/索引/缓存）面对频繁小变更时，用「内容指纹」判定是否真的需要重算，只重算指纹变化的子集；指纹必须与重算逻辑用同一套解析器，否则基线对不上。

## 防复发
- [ ] 指纹生成与增量重算必须共用同一解析器（Understand-Anything 的 build-fingerprints 用 TreeSitterPlugin + PluginRegistry，与 extract-structure 完全一致），否则基线漂移
- [ ] 指纹写入时机必须早于元数据（先成功生成指纹再写 meta），否则后续每次 commit 都误判为全量变更
- [ ] 数据目录写入要避开易失路径：git worktree 下写到主仓库根而非 worktree 目录，否则会话结束产物即丢（见 worktree 系列经验）
