# 同文件并行追加段的合并：用「基线+各分支追加段」重建，勿用 OURS+THEIRS 字符串拼接

## 症状

AI自动获客二期两处「同文件两分支各自追加独立段」的显式冲突：

1. **28（发布 Runner）/ 31（养号 Runner）同改 `index.js`+`ipc/router.js`+`index-integration.test.js`**：合并时 index.js 冲突块是「deps 解构里两票都映射同名 `createMonitor` 变量」、router.js 是「两段 JSDoc+函数签名」、test 是「两个 runner mock 嵌套」。
2. **36（聚合视图）/ 39（大屏）同改 `router/index.js`+`api-client.spec.js`+`router.spec.js`**：router/index.js 冲突是「两票都改同一行 `ROUTE_NAMES` 数组」、两个 spec 是「重复 it 块缺闭合」。

第一次我用「按 OURS+THEIRS 段拼接」的自动脚本解决 → 产生**结构破坏**：index.js workPublish 对象缺 `});` 闭合、forwardLog 赋值嵌套、router.js 注释区重复、test 文件 31 的 runner mock 嵌套进 28 的测试且 28 测试主体丢失。靠 node --check + 括号平衡分析逐个定位修复。

## 根因

「各自追加独立段」的冲突有两类，处理方式不同：
- **同一行/同一常量两边都改**（如 `ROUTE_NAMES` 数组）：拼接会生成两行相同声明 → 重复导出/重复声明，必须**合并内容**而非拼接；
- **不同位置各自追加**（如 index.js 的两个 Runner 装配块）：理论上可顺序拼接，但 git 冲突块是按「最近的共同祖先行」划分的，拼接结果常把一段嵌进另一段（缺闭合括号）、或把语法半截拼在一起。

`<<<<<<<` 块是「行级 diff 的并集」，不是「语义上的两个独立单元」——按块拼接假定两边块互不嵌套，这个假定在共享装配文件里经常不成立。

## 代价

两处冲突各一轮「自动拼接 → 语法/结构破坏 → 手工逐处修复 → node --check + 全量测试验证」；28/31 那次还破坏了 test 文件的 runner 块，需从两个源分支提取追加段重建。

## 教训

**同文件两分支并行追加段、合并产生显式冲突时：**
1. 首选「**从共同基线重建**」：`git show <基线>:<file>` + 各分支相对基线的追加段（各自文件尾部增量）按顺序拼——两票都从同一基线出发时，追加段天然有序，零嵌套风险；
2. 若必须手工合并冲突块：**先分类**——「同一行两边改」→ 合并内容；「不同位置追加」→ 顺序拼接，并检查拼接处括号闭合；
3. 任何合并解决后，**必须跑全量测试 + 语法检查**（node --check / 括号平衡），不因「git 说 resolved」就提交。
