# 重构批次：行为变更先红测钉死，纯搬迁借既有测试绿证明

## 症状
候选 4（角色字段装配收敛）里夹带一个行为变更（解析出的 postHistoryInstructions 落库），候选 5（抽 ChatRound）是纯搬迁。如果两者混在一个断言里验证，行为变更的回归与搬迁的疏漏互相掩盖。

## 根因
重构批次常同时含「行为变更」与「行为不变的搬迁」两类改动，但验证手段不同：变更需要**新红测钉死目标行为**，搬迁没有新行为可测——它的正确性证明是**既有测试原样绿**（公开接口零变化时，1260 行旧测试就是回归证明）。

## 代价
若用同一条断言验证两类改动：搬迁改错了接口，旧测试红了一片，分不清是搬迁错误还是变更预期；变更没写红测，静默行为偏差可能只在新路径上露出。

## 教训
- 行为变更点：先写红测（断言目标行为）→ 实现 → 绿，红测只盯变更点；
- 纯搬迁：落新文件 → 改消费方委托 → **公开 API 零变化前提下既有测试原样绿即零回归证明**，新测试只补「新模块可独立测」的契约，不重复旧断言。

## 防复发
- [x] 开工前列清单：本批哪些是行为变更（须红测）、哪些是搬迁（借旧测绿）；
- [x] 搬迁批的 commit 信息注明「公开 API 零变化」，review 按此核对。
