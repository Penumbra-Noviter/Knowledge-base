# 第三方 API 集成：第一步必须抓真实响应做 fixture

## 症状
kkrb.net 客户端（L 系列）三处独立错误叠加全部失败：① 缺 `X-Requested-With: XMLHttpRequest` 头，接口返回 `code=-101 系统繁忙`；② CSRF 握手假设首页有 `<meta name="csrf-token">`（实际不存在）；③ 响应解析基于**手写测试数据**，字段名/结构与真实 API 完全不同。修复后 2 小时又发现字段语义映射错（`hourlyProfit`/`productionTime` 被当成利润/出售时段）。

## 根因
未验证真实数据就开始写解析器；测试夹具是「想象出来的 schema」。请求头、凭证握手、响应 schema 是三个独立出错环，任何一环凭假设都会全盘失败。

## 代价
3 次修复往返（`5a8bc23` 重写解析 + `68b0663` 再纠字段语义 + L-04 数据源功能整个删除）；期间功能不可用。

## 教训
**集成第三方 API 时，第一条代码是「抓一份真实响应存成 fixture」**——用真实响应驱动解析器与测试数据。手写 mock 数据通过测试 ≠ 集成成功，mock 与真实 schema 的偏差会在上线后以最难排查的方式出现（数据对但字段错）。

## 防复发（惯例：开工预检时对照执行，无需勾选；动作项见条目内去向）
- [x] 修复后 `tests/test_kkrb_client.py` 已改用真实格式
- 新第三方集成：抓真实响应（含错误响应）→ 存 fixture → 再写解析
- 同步验证请求头/凭证握手/响应 schema 三环，不跳过任何一环
