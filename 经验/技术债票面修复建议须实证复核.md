# 技术债票面的修复建议本身须实证复核

## 症状

TD-15 遗留描述：「守卫过严收窄——`#setting-custom-model` 缺 + 非 `__custom__` 模型时拒绝本可成功的保存」，票面建议改法为「providerSelect.value === '__custom__' 时方要求」。Grilling 实证发现：provider 下拉由 `initProviderDropdown` 只填 providers key（settings-panel.js:40-42），**永不为 `'__custom__'`**——自定义语义键在**模型**下拉。按票面写则条件恒假，守卫对 custom 输入形同虚设（比原守卫更糟：连 `__custom__` 模型的保护都丢了）。

## 根因

审计（Falsify 观察）只描述了「守卫边界 > 旧崩溃边界」的现象，给出了一个**未经验证的修复方案**。审计快照会过期（已有教训），但票面建议的**方案正确性**是另一层风险——描述现象的人不必然理解正确修法。

## 代价

若按票面执行：守卫对 custom 输入失效（`__custom__` + custom 缺会静默放行而非 warn 早退），TD-13 守卫体系出现静默退化；测试用例 B（基线绿钉保留边界）会红，但若没有该用例则缺陷无声上线。

## 教训

**执行技术债条目时，「做不做」和「怎么修」都要实证复核**：

1. 票面建议的修复方案 = 候选假设，不是结论——先读代码验证方案在真实代码上是否成立（下拉 value 的实际取值来源）
2. 守卫/条件类修复必须与**裸读分支**精确对齐：守卫条件应镜像实际访问该元素的代码路径条件（getSelectedModel 仅当 `modelSelect.value === '__custom__'` 触碰 customInput → 守卫条件同源）
3. 修正票面方案时在共识/归档中显式记录「票面建议被否定 + 实证理由」，避免后人按票面重做

## 防复发（惯例：开工预检时对照执行）

- [x] TD-15 守卫条件修正为 modelSelect 口径 + 归档注记票面否定理由
- 后续守卫/条件类技术债：先查下拉/输入的实际 value 来源域，再定条件
