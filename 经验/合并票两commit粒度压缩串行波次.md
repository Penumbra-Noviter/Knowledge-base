# 合并票两 commit 粒度压缩串行波次

## 症状

td-consume-25 批次显示族 4 票（T-5 gamma DLL 收敛 → T-6 文案单源 → T-7 状态判据 → T-8 收口）共享 display_gamma/display/display_page 文件，文件冲突图强制严格串行——原方案 5 波（每波 1 票显示族 + 其他），串行波次摩擦大（每波 worktree/merge/增量审核各一次）。

## 根因

波次机制按「票」为单位，但票的粒度是可调的：共享文件族内的连续重构只要每张票内部是**可独立提交的最小连贯阶段**（各 commit 有独立验收 + 独立测试），就可以合成一张「合并票」，票内两个 commit 分列文件范围（c1 源 1+测 1、c2 源 3+测 2），票级验收条数合并计（8 条，≤8 硬上限）。

## 代价/收益

原 5 串行波 → 3 波（波 1 三票并行 + 波 2 两票并行 + 波 3 合并票），显示族串行链成本减半；merge 次数 5→3；增量审核 5→3。代价 = 票内两 commit 的依赖关系由实现者自持（c2 依赖 c1 已合并），凭证 = 两个 commit 摘要各自独立。

## 教训

1. **串行族合并票的前提**：同一文件族 + 每 commit 可独立验证 + 票级验收 ≤8 条 + 源文件数硬上限内——四条缺一不可；合并票是「两 commit 粒度」不是「一票吞两特性」（后者违反切票粒度）。
2. **计划阶段就定**：合并方案在 Grilling 共识的波次分组里拍板（「替代方案 = 合并两票」），plan-tickets 按合并票落文件范围（c1/c2 分列），Implement prompt 明确「两个 commit 独立提交、各有测试」——不是执行中临时决定。
3. **已知边界**：合并票的验收 8 条上限是票级合并计，若两票各 5 条合并 10 条即超限——合并前先加验收条数。

## 防复发

- 后续批次遇共享文件族串行链 >3 波时：Grilling 共识阶段评估合并票（前提四查），plan-tickets 按 c1/c2 分列文件范围落票。
