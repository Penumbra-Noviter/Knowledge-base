# 第三方引擎静默失败面——验收须「产物+success+日志」三查

## 症状
hy-memory 两种失败形态都不抛异常：
- **embedding 端点不可达**：`add()` 重试 3 次后返回 `{"success": false, "error_code": 500, "error_message": "Connection error."}`，错误只落在服务端 ERROR 日志（含完整 traceback）
- **无效 LLM key（pro 提取模式）**：`add()` 返回 `success: true` + fact/experience **全空**——成功旗标为真、产物为零，失败只落服务端日志

## 根因
这类摄入引擎把「调用完成」与「远端能力可用」解耦：调用方视角是请求送达并拿到结构化响应对象，真正的失败（embedding/LLM 远端不可达、key 无效）被吞进 success 旗标或全空产物，只留服务端日志。**异常机制不承载业务失败。**

## 代价
只查异常或只查 success 旗标都会漏判：前者在「不抛异常」路径上接收不到 false 分支（漏检）；后者在 success:true 时把全空摄取当成功（写库产物为空、索引无效），摄入空转无告警。若不修为「产物存在性 + success + 日志」三查，T-01 索引器 / T-03 插件会静默产出空索引。

## 教训
集成这类引擎，验收/卫代码以**「产物存在性 + success 字段 + 服务端日志」三查**为准——不能只查异常，也不能只查 success 旗标。「success:true + 产物为空」是必须单独覆盖的失败形态。
