# 回归测试必须锁定真实缺陷路径

## 症状

T-A1 修「搜索视图重复调用 initSearchView 双绑事件导致搜索双发」。首版回归测试按工单字面描述写（防抖路径输入触发两次搜索），实测在旧实现下**恒真**（红不起来）——无法证明守卫有效。

## 根因

双绑的 input handler 共享**模块级 `searchTimeout`**：同一次派发时后绑的 handler 会 `clearTimeout` 掉先绑的定时器，防抖路径**天然免疫双发**（每次 input 事件只留最后一个定时器）。真实双发点在 **Enter 立即搜索路径**：keydown 双绑无互斥，一次 Enter 必然执行两次 `performSearch`。

## 代价

若按症状路径交付测试，守卫实现错误也不会被测试抓住——测试通过 ≠ 缺陷被防住，产生虚假安全感（比没有测试更糟）。

## 教训

**「测试先红」是硬验收**：回归测试写完后必须在**旧实现上运行一次确认红**，红不起来就说明没锁住真实路径，要解剖缺陷机制找真实触发点（共享状态免疫 → 找无互斥的路径），而不是改测试断言硬凑。

## 防复发（惯例：开工预检时对照执行）

- [x] T-A1 最终测试锁定 Enter 双发（旧实现红：3 次请求 vs 预期 2 次；守卫后绿：恰 2 次）
- 后续所有「双发/重复绑定」类回归：先找共享状态互斥点，再找无互斥路径作为测试锚
