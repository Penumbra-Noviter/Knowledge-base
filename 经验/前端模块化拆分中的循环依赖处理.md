# 前端模块化拆分中的循环依赖处理——钩子函数模式

## 症状
前端 `app.js` 从 1380 行拆分出 `chat.js`（328 行，聊天逻辑）和 `state.js`（54 行）时，遇到了循环依赖问题：`chat.js` 中的 `handleSend` 需要调用 `app.js` 中的 `loadConversations`（刷新对话列表），但 `app.js` 又 import `chat.js` 的渲染函数来初始化和渲染聊天界面。

## 根因
ESM 的 import 是静态分析的，A → B → A 的循环依赖会导致执行时拿到未初始化的绑定，引发 `TypeError: X is not a function`。问题的本质是**拆分出来的模块需要回调到父模块**，但模块图是单向的。

## 代价
设计了 `setConversationsRefresher` 钩子模式：`chat.js` 暴露一个 `setConversationsRefresher(fn)` 函数，`app.js` 在初始化时把自己的 `loadConversations` 注入进去，`chat.js` 内部调用 `refresher()` 即可。避免了循环 import，且依赖方向明确（chat → app 的单一回调）。

## 教训
**前端模块拆分遇到循环依赖时，用「注入钩子」模式而非「互相 import」**：

```js
// chat.js — 暴露 setter，不直接 import 父模块
let _refreshConversations = null;
export function setConversationsRefresher(fn) { _refreshConversations = fn; }
export async function handleSend() {
  // ... 发送完成后 ...
  await _refreshConversations?.();
}

// app.js — 在初始化时注入
import { setConversationsRefresher, handleSend } from './chat.js';
import { loadConversations } from './app.js';
setConversationsRefresher(loadConversations);
```

这比把父模块函数传参到每个调用点更干净，也比引入 EventBus 更轻量。
