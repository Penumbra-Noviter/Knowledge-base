# 依赖活服务的自检须排在服务重启之后

## 症状

升级 dsh 核心的验证阶段，按插件逐个跑自检。`dsh-hy-memory` 的 `self-test.mjs` 输出：

```
== 3) 真实 server 往返（19527，主会话 ctl 托管实例） ==
  ✗ FAIL: healthz ok（{"ok":false,"error":"fetch failed"}）
  ✗ FAIL: searchHttp 往返失败：hy-memory 服务不可达：fetch failed
InvalidResponseError: hy-memory 检索响应异常：memories 缺失或非对象
exit=1
```

看起来像「升级导致插件与记忆服务通信中断」——一个典型的升级回归信号。

## 根因

前 3 段（配置合并优先级、search 请求拼装）是纯逻辑，全部通过；从第 3 段起测试需要**真实的 hy-memory 服务**（19527/19528 两个实例）。而升级流程的第一步就是**停服**——为了替换核心文件，`taskkill /T` 把 dsh 主干连同它拉起的两条 hy-memory 子进程一并杀掉了。

于是测试跑在一个**服务必然不在**的窗口里。`fetch failed` 反映的是测试环境未就绪，与被测代码无关。

## 代价

- 一次假阴性。若不深究就会得出「升级破坏了 hy-memory 集成」的错误结论，进而去排查根本不存在的回归。
- 自检报告里出现 `✗ FAIL` 与未捕获异常（`InvalidResponseError`），观感上极像真实故障，具有误导性。

## 教训

**验证有时序约束：依赖活服务的自检，必须排在它依赖的服务重启之后。** 升级/重装类任务里，「停服 → 换文件 → 打补丁 → 重启 → **然后**才跑服务依赖型自检」是唯一正确的顺序。在停机窗口内跑这类测试，得到的失败是环境缺失的假阴性，会把验证者引向错误方向。

推论：看到 `✗ FAIL` 先问一句「这个测试现在**有没有条件**失败」——断网、服务未起、端口未监听、依赖未装，都会制造与被测对象无关的红。

## 防复发

- [x] 升级流程的执行顺序固定为：停服 → 备份 → 安装 → 重放补丁 → **重启服务** → 回跑服务依赖型自检
- [x] 纯逻辑段与需活服务段在测试内部已分段（`== N) 标题 ==`），可据此判断红落在哪一类
- [ ] 未落实：自检入口在前置检查里探测服务可用性，不可达时以「跳过（环境未就绪）」区别于「失败」，避免停机窗口内的假阴性
