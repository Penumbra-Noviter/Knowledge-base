# 集成插件静默跳过 = 从未生效，排查须要正向证据

## 症状

dsh 的本地插件 `dsh-auto-retry` 每次页面加载都在控制台打印一次：

```
[dsh-auto-retry] connection.api 不可用，跳过
```

它只是 `console.warn`（不是 error），页面其余功能全部正常、没有任何崩溃，因此被判定为「插件自身的防御逻辑，非错误」，写进了会话记忆并在升级报告里作为「已知但无害」一行带过。真实状态是：**该插件自安装以来从未生效过**——监听器从未启动、设置卡片从未注册、功能从未运行过一次。

## 根因

两层叠加：

1. **插件依赖了一个不存在的 API。** 它读取 `ctx.get('connection')` 后检查 `connection.api`，而 connection 服务的实际结构是 `{ isLoopback, generation, state, rpc, reconnect, ... }`——**它从没有 `api` 属性**（逐字核对了三个历史版本，结构一致）。插件作者写的是更早期/想象中的 API 形态。
2. **防御式跳过把「接不上」伪装成「正常降级」。** 代码路径是 `if (依赖缺失) { warn(...); return }`——这是好习惯（不崩溃），但它让**失效与正常运行产生同样的外部表现**（页面正常、无 error），唯一的信号是一行容易被合理化的 warn。再加一句注释/说明「这是插件自身的容错」，失效事实就被彻底掩埋了。

## 代价

- 该功能长期不存在，而我在上一轮升级验证中**主动把它判定为「非错误」并写入记忆**——错误结论会在后续会话持续误导（记忆被当作事实引用）。
- 本次排查花费约十余轮工具调用：先按「0.1.6 破坏了插件」的假设去查时序、加载顺序、bundle 顺序（全是错误方向），直到逐版本核对 `provide("connection", handle)` 的 handle 结构，才发现 `api` 从来不存在。
- 若没有这次「顺手修一下」，失效可以无限期存活——因为它不产生任何 error。

## 教训

**「有警告但不算错误」不是结论，是待验证的假设。** 判断一个集成是否工作，只认**正向证据**（功能真的跑过、副作用真的产生过、状态真的变更过），不认「没有报错」。当依赖获取失败时存在静默降级分支（`if (!dep) return`、可选链短路、try/catch 吞异常），就默认它是可疑的——因为这类代码会把「从未工作」和「正常工作」渲染成同一种外观。

具体到本类问题的验证手法：拿运行时的**对象形状**去对（`Object.keys(服务)`），而不是猜时序；跨版本核对同一段实现，若某个属性在所有版本都不存在，那它不是「版本演进删掉的」，而是「从来就写错了」——这两种结论导向完全相反的修复方向（迁移 vs 一直没接上）。

## 防复发

- [x] 已落实：修复 dsh-auto-retry，改用真实存在的 `ctx.sessions` 服务与 `sessions.binding(id).eventSource`，并把 API 契约（含两个反直觉约束）写进记忆 `dsh-client-plugin-api-contracts`，供后续写 client 插件时先对表
- [x] 已落实：浏览器实测以正向证据验收——设置卡片是否真的出现、启动扫描日志是否真的打印、UI 改设置是否真的持久化
- [ ] 待养成的习惯：验证第三方/历史插件时，先问「它的关键副作用是什么」，再去运行时找那个副作用存在过的证据；找不到就是没生效，不看它是否报错
- [ ] 可选结构性措施：给本地插件加一条「启动自检」——依赖缺失时除 warn 外，在设置页/插件列表显示显式的失效状态（让失效可见，而非只留一行控制台警告）
