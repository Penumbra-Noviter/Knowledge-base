# 同一产物文件的多个写入方必须共享格式契约单源

## 症状
编辑器导入 Ren'Py 游戏目录（Agent17），自动提取成功后弹窗：「提取完成后加载项目数据失败：无法加载 ...\\.hanhua\\extracted.json: Missing required key 'extracted_strings'」。CLI 提取产出的 `extracted.json` 能正常加载，编辑器自动提取产出的同一文件加载必失败。

## 根因
`extracted.json` 存在两个写入方，产出不同 JSON shape：

1. **CLI 提取器**（`renpy/extractor.py`）写包装字典：`{"extracted_strings": [...], "extracted_count": N}`
2. **PipelineOrchestrator**（`save_phase_product` → `_encode_value`）写裸数组：`[{"__type__": "ExtractedString", ...}, ...]`

读取方 `read_extracted()` 只实现并测试过包装字典格式（编辑器测试夹具 `_make_extracted_data` 也只造这种），对裸数组执行 `"extracted_strings" in data` 恒 False → 抛「Missing required key」。编辑器自动提取恰好走 orchestrator 路径，于是系统里最主流的入口（打开即提取）必然触发该错误。`_entry_from_json` 用 `.get()` 静默吞掉 `__type__` 字段，也掩盖了格式分叉信号。

## 代价
用户导入主流游戏路径（自动提取）必然失败一次；定位需跨 4 个模块（extractor / orchestrator / io 读取 / 测试夹具）核对格式，约 20 分钟。无数据丢失，但因「提取成功→加载失败」的报错时序极具误导性（用户以为提取坏了，实际是格式契约问题）。

## 教训
**同一产物文件存在多个写入方时，格式契约必须单源**——所有写入方共用同一序列化函数（或共享 schema），新写入方不能自造 shape。读取方测试必须覆盖**所有写入方的真实输出**作为夹具，而不是只用测试里常见的一种形态；「读取方只兼容自己见过的格式」是隐性契约，第二条写入路径接入时必定崩溃。

修复取向：读方宽容兼容（双格式 normalize）是防御性下限，不是终点；治本是写入方统一序列化入口，否则格式继续分叉。
