# 复核关闭的前提会失效——架构评审须重估关闭理由

## 症状

架构走查给出 5 候选，其中 2 个是「第 2 次建议」（与历史复核关闭项同源）：C1（删 `types.build_cli_tokens`，同源 TD-66/TD-78）、C4（DisplayPage 动作族收口，同源 TD-62）。若按「复核关闭 = 已裁决，不重提」的机械规则，这两条会被直接剔除——但两条的关闭前提都已失效：

- TD-66 关闭理由「build_cli_tokens 的 (tool, values) 是双入口公共契约」——T-061/T-067 后 runner/display 已直调 codec，只剩 GUI 两点挂转发，声明的「双入口共用」失真
- TD-78 关闭理由「函数体延迟导入是标准消环模式」——转发层删除后延迟导入环本身消失
- TD-62 关闭理由「三职责共享同一状态模型，拆会拆散」——ADR-025 已把状态/数值模型抽入 SliderBinding，页面只剩 Qt 装配 + slot 编排

## 根因

复核关闭是**当时事实**的裁决（「当前无真实痛点」），而关闭理由里的前提（谁在用、共享什么、模型在哪）会随后续重构改变。关闭记录本身不携带「前提失效检测」——读关闭表的人容易把结论当永恒事实。

## 代价

若机械剔除：C1 的浅转发（interface 声称公共、消费方已绕过）与 C4 的增量膨胀（772 行热点文件）永久封存，且关闭理由本身变成误导文档。

## 教训

1. **「第 N 次建议」不是重复，是重估信号**：走查命中复核关闭表同源项时，先复读关闭理由里的前提句（谁消费/共享什么/在哪里），逐条对当前代码验证；前提失效 → 标注「第 N 次建议，前提已变」正常提案，并说明哪条前提失效。
2. **关闭记录带前提条件**：写复核关闭理由时，把「本条关闭成立的前提」写成可验证句（如「rank 与 GUI 共用 X」），下次走查可直接 grep 验证。
3. **ADR 变更会批量使关闭前提失效**：ADR 抽走某模型/改判某职责时，顺手扫一遍同族复核关闭项（本批 C4 即 ADR-025 的连带影响）。
