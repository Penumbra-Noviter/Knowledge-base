# 合并后契约回归须跑全量或静态守卫——波末只跑受影响模块会漏契约违例

## 症状
M3（角色+搜索）W3 合并后，`view_theme_tokens_test` 静态不变量红：`search_view.dart`（M3-04b）与 `chat_view.dart`（M3-04c）共 8 处直接引用 `ConverColors`，违反 F-7「视图层 token 契约」（须经 `ConverPalette`/`colorScheme`）。两票各自波末只跑了受影响模块测试（views/search、views/chat），静态不变量组 `test/views/view_theme_tokens_test.dart` 不在其内——违例随 merge 进主分支，直到 M3-03 全量回归（685 测）才发现 1 失败，期末才修复。

## 根因
波末增量审核与波内验证按「受影响模块」圈定范围，契约守卫测试（静态不变量扫描全目录）不在受影响的单一模块内——F-7 这类「lib/views/** 不得含某标识符」的**跨文件契约**，任何新增视图都可能违例，但其对应测试文件不受「本工单改动哪个模块」影响，天然漏出受影响集。

## 代价
两处契约违例在合并时未被拦下，主分支带着红测试滚动了两轮；若没有期末全量测试兜底，违例会静默进入交付（视图 token 契约被破坏、深浅色正确性风险）。修复本身简单（8 处改经 colorScheme/palette），但暴露时机晚了两波。

## 教训
**并行波合并后跑「受影响模块 + 全库静态契约守卫」**——契约类测试（静态不变量 / layer boundary / token 合约）是合并的必跑项，不能只在单工单验证时跑。更稳妥：波末合并后直接跑全量（成本高时至少全视图层 + 静态守卫组）。「受影响模块」定义要含**契约守卫测试文件本身所守卫的全目录范围**。
