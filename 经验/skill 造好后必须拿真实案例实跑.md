# skill 造好后必须拿真实案例实跑（结构校验 PASS ≠ 行为可用）

## 症状
- product-facets skill 用 skill-authoring 的 `quick_validate.py` 校验 PASS（"Skill is valid!"）：文件齐全、frontmatter 合法、引用不断链。
- 但拿一个假设项目（「会采集用户数据的桌面工具」）实跑一遍，立刻暴露缺陷：推导出的「隐私/数据面」被判为「深」（最高优先级），而它的落地协议**是空的**——只有一句占位草图，给不出任何设计/落地/校验步骤。

## 根因
- 校验工具（quick_validate / 结构检查）只查**结构**：frontmatter 合法、目录结构对、引用的文件存在。它查不出**知识层空缺**——某个被声明为高优先的分支，其协议是否真的存在、是否自洽、能否落地。
- 更一般：**声明的完整度 ≠ 实现的完整度**。skill 的骨架（workflow / 输出契约）可以先写全，但知识层（每面协议、每条分支）可能留空，而结构校验对此完全无感。

## 代价
- 不实跑就交付，skill 会带着「命门处给不出方案」的缺陷上线：用户第一次真用它处理该类项目（采集/隐私类）就撞上，返工成本远高于造时跑一遍。本例若不实跑，这个缺陷会一直隐形。

## 教训
- **造/改 skill 后，结构校验 PASS 只是入场券；必须再拿一个真实（或具体假设）案例实跑一遍**——走完 workflow，检查输出是否自洽、被标「深/高优先」的分支是否有真实协议、执行路由是否断链。
- 「被声明为重要」的分支，其协议不能停在草图：skill 在命门处的空缺，只有实跑照得出来。
- 实跑案例要**与目标场景异质**（本例刻意用「采集类项目」而非「桌面工具」），否则同类案例会自证。

## 防复发
- [ ] 造/改 skill 的完成判据固定为「结构校验 PASS **且** 真实案例实跑产出自洽输出」，写进 dao-skill Completion Contract 的验证项。
- [ ] 实跑后逐项核对：被标「深」的分支，是否有对应的真实协议（非草图）。
