# 新工单编号须先查处置记录防撞号

## 症状

洁癖收尾时发现：本轮完成的桌面窗口控制工作用了「TD-26」，而 TECH_DEBT 处置记录（同一天、TD-25 会话）里 **TD-26 = interrupt-redirect-integration 停跑测试（❌ 不立项）**、TD-27 = superseded 标注（❌ 不立项）。同一编号指向两个完全不同的东西。

## 根因

编号领取只看了 TO-TICKETS 归档表，没查 TECH_DEBT 处置记录——「❌ 不立项」的处置条目不进 TO-TICKETS 归档，却占用了编号。`pool_cleanup_check.py` 门禁只校验「脚注最大编号 = 全库最大编号」，TD-26 作为归档行进入后脚注显示的最大编号被推到 TD-28，门禁才在第二次跑时抓出不一致——**撞号本身门禁不拦**（一个在归档、一个在处置记录，语义位置不同）。

## 代价

- 收尾轮多一轮全局 grep 重编号（TO-TICKETS + DEV_LOG + 记忆三处）
- 若没被洁癖审计抓住，两份文档里同一个 TD-26 指向不同主题，后续追溯必踩

## 教训

**「✅ 修复」「❌ 不立项」的处置记录都占用编号**。发新工单号前，除了看 TO-TICKETS 归档，还要 grep `TECH_DEBT.md` 处置记录 + 候选区的最大编号——两个表是同一个编号空间。

## 防复发

- 发号前：`grep -n "TD-" TO-TICKETS.md TECH_DEBT.md | 取最大编号 +1`，且核对「最大编号」最近几次处置是否把号用掉
- 编号空间收敛建议（可选）：处置记录与归档共享单调序列，脚注标注「全库最大编号（含处置记录）」——门禁校验逻辑也按此口径
- [x] 已落实？（本轮重编号 TD-28，脚注已同步为「当前最大 TD-28」）
