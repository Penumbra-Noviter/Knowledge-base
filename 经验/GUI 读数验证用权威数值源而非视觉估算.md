# GUI 读数验证用权威数值源而非视觉估算

## 症状
- 音量调 0 任务中，同一张 sndvol 窗口截图两次派 View 子智能体读滑块位置，给出矛盾读数（第一次「Speaker 13%、系统声音/ZCode 1-2%」，第二次「Speaker 23.7%、另两列 0%」），且轨道边界像素测量也不一致。
- sndvol 滑块是自绘 Pane（UIA 读不到 RangeValue），UI 树里没有数值可用。

## 根因
- 视觉模型对**像素位置/百分比**的估算本质是主观量级判断，受图像缩放、渲染细节、模型注意力影响，两次读同一图都可能漂移——它适合「是否有障碍/是否接近底部」这类定性判断，不适合「精确数值」。
- 验证需要「到底了没有」的精确答案，视觉估算的误差会被当成「还没到」。

## 代价
- 两次 View 往返（约 2 分钟）+ 方向误导：View 报告「静音图标」与「滑块未贴底」促使额外按了 100 次音量键，实际系统早已静音且按键无视觉反馈。

## 教训
- **精确数值判定不依赖视觉估算**：优先找结构化权威源——Windows 是任务栏音量图标的 UIA Name（直接含「已静音/0%」）或日志/API 读数；只有权威源不可得时才退回视觉，且要标注「估算、置信度低」。
- 视觉返回的「像素级数字」不可作为验收依据，须与权威源交叉核对。

## 防复发
- 任何需要「数值型验证」的场景（音量/亮度/进度条/坐标），先枚举结构化权威源（UIA Name、RangeValuePattern、API 返回值、日志），视觉只做辅助定性。
- 截图对比（md5/像素 diff）只用于「有没有变化」，不用于「数值是多少」。
- [x] 已落实（任务栏图标 UIA Name 作为音量权威源已记录于 memory audio-mute-windows）
