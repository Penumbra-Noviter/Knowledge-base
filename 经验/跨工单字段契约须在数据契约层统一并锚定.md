# 跨工单字段契约须在数据契约层统一并锚定——camelCase/snake_case 静默丢字段

## 症状
三期直播调度 Wave-1：工单 06 `buildLiveUserRecord`（Electron preload）输出 camelCase 键（`secUid/webcastUid/userUrl/messageId/eventTimestamp/profileAvailable`），工单 02 `normalize_live_record`（FastAPI 后端）消费 snake_case 键（`sec_uid/webcast_uid/user_url/message_id/event_timestamp`）。两条链各自单测全绿，直接对接后：identity_type profile→numeric 降级、sec_uid/webcast_uid/user_url/message_id 全 None、event_timestamp 变 now()——字段静默丢失，无任何报错。

## 根因
spec §6.2 自相矛盾：声明「以 reverse buildLiveUserRecord 输出为契约」但示例字段是 snake_case，而 reverse 实际输出 camelCase。06 跟随 reverse（High 置信度逆向直读），02 跟随 spec 示例（snake_case）。**无任何工单定义 camel→snake 转换层归属**——波内各票文件范围互不相交，每个 Implement 只在自己文件范围内自洽。

## 代价
唯一跨工单阻断（F-1）。仅靠波末增量审核 Falsify 轴发现（真实运行 06 输出送入 02 归一化对比）；修复需派回 06 统一 snake_case + 改两套测试断言 + 加跨契约锚测试。若进 UI/真机才暴露，代价更高。

## 教训
跨工单传递的数据契约（字段命名/序列化约定）是**模块边界上的真实 seam**：必须在 spec 的 Data Contracts 层显式统一（选一个命名权威，标注「本链路全程使用 snake_case，各票实现以 spec 契约为准」），不能「各自跟随 reverse / 跟随 spec 示例」两头飘。上游 JSON 输出与下游反序列化消费的键名不一致时**静默丢字段不报错**——比显式类型错误更危险。

## 防复发
- [x] spec 数据契约节加「命名权威」声明（三期 spec §6.2 已补：统一 snake_case，FastAPI 权威侧）
- [x] 跨契约锚测试：GiftMessage 样例 → buildLiveUserRecord → 断言输出键为 snake_case（消费方键一致）
- [x] 跨栈实证：Electron 输出直接送入后端 normalize_live_record 断言字段保留（identity_type/sec_uid/message_id/event_timestamp）
- [ ] 波末增量审核 Falsify 轴保留「跨工单字段契约直连」检查项
