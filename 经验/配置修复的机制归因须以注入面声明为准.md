# 配置修复的机制归因须以注入面声明为准

## 症状

修「terminal-bash 永久 pending（waiting for service: terminals）」时，按 patch 注释与直觉把修复价值写成「侧边栏终端是产品面能力，删除配置等于放弃 pwsh 意图」。期末 code-review 指出：`dsh-api-terminal-controller` 的 `static inject = ["subprocess","sandboxPolicy","workingDirectory","typert"]`，创建终端走 `subprocess.spawnTerminal`，**根本不消费 `terminals` 服务**——注释、spec、DEV_LOG 三处把机制归因写错。

## 根因

- 技术债条目与 patch 注释自带的机制叙述被当成了事实（「侧边栏终端需要它」），没有反向核对服务的**提供者与全部消费方**。
- cordis 风格 DI 的真实消费关系只写在两处：提供者 `super(ctx, "serviceName")`，消费者 `static inject = [...]`（或 `inject = [...]` 数组）。看 UI/注释/包名推测归因，会在「同名字概念」（terminal vs terminals vs subprocess.spawnTerminal）上想当然。

## 代价

- 评审返工一轮：patch 注释、spec「决策 1」、DEV_LOG 处置段、evidence Falsify 行共 4 处改写；修复方向本身没错（补 pty 消除 pending 依然成立），但价值叙事整体重写。
- 若未被发现，会把「侧边栏终端 pwsh 默认」误记为已解决——真正的通路（`terminal-controller.config.shell`）仍是未配置状态。

## 教训

修配置级问题前，先建「服务提供者 ↔ 消费者」清单：grep `super(ctx, "…")`（提供者）与 `static inject` / `inject = [`（消费者），以此为准写归因；条目自述、注释、包名相似度都不是依据。
