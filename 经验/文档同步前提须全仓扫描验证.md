# 文档同步类工单的前提必须全仓扫描验证

## 症状

TD-2「契约表版本标签 v1→v2」工单按审计快照写「tests/docs/Rust 侧已是 v2，零改动」，Implement 开工前 grep 全仓发现 test_migrate_data.py 与 test_packaging.py 各 2 处**陈旧 v1 标签**（真实漂移，非历史叙述）——「零改动」前提事实错误，范围被迫扩展 4 处。

## 根因

审计/共识产出的「某侧已是 X」是**时间快照断言**，不是扫描结论。上一批次（技术债 16 项清零）只改了目标文件，未对「已 v2」侧做 grep 核验，漂移留在测试文件里被快照掩盖。

## 代价

若按原范围执行：v1 标签残留测试文件，下次复核再捡一次债；若按扩展执行（本次）：范围申报与主会话核验多一轮沟通。成本小但暴露「前提核查不彻底」的系统性风险。

## 教训

**「已是 X / 零改动」类前提必须 grep 验证，不能信任审计快照**：

1. 文档同步类工单的验收标准写成「grep 归零」比「改 N 处」可靠——扫描驱动而非清单驱动
2. 但要区分**当前状态标签**（该改）与**历史叙述**（不该改——描述旧编码/防回归锁，改写会篡改语境）：grep 结果逐处定性，不能一刀切
3. 验收口径问题（如「grep 归零字面不可达」）在归档时显式注记，不悄悄放过

## 防复发（惯例：开工预检时对照执行）

- [x] TD-2 扩展 4 处同类漂移已修 + 申报记录
- [x] 归档注记：grep 归零口径 = 版本标签归零（历史叙述白名单豁免）
- 后续文档同步工单：先 `grep -rn <旧值> <范围>/` 全仓定性（标签 vs 叙述）再定改动范围
