# 跨语言镜像契约必须对真实消费者做连接级验证

## 症状

ARC-9 T-04「壳注入 DATABASE_URL 编码对齐」：Python 侧 `test_data_dir.py` 与 Rust 侧 `server_test.rs` 建立**契约表 v1 双端镜像**——两测试文件互相印证同一组字符串级预期（空格/中文/`#`/`%` → `%XX` 编码），全量测试全绿。期末四轴审核 Falsify 轴构造真实连接才发现：壳注入的 URL 由 **SQLAlchemy** 消费，其 sqlite 方言对 `%XX` **零解码**（`%20` 被当字面文件名）→ `OperationalError: unable to open database file`。Windows 用户名含空格（默认 `%APPDATA%` 路径）与任何含空格/中文的 `CONVER_DATA_DIR` 全部从「基线可用」变为「数据库打不开」。

## 根因

「对齐迁移脚本 URI 语义」是**范畴错误**：migrate_data `_open_readonly` 走 `sqlite3.connect(uri=True)`（SQLite URI 规则**会**解码 `%XX`），而壳注入 URL 的消费者是 SQLAlchemy（**不**解码）。两个消费者解码语义不同，双端镜像测试只验证了「我编码的字符串 == 我解码的预期」，从未验证「真实消费者能否用它打开数据库」——镜像互相印证，盲区共享。

## 代价

1 个阻断回归（期末审核抓出，基线行为被破坏）+ 契约表 v1→v2 重做（编码集收窄至仅 `?`→`%3F`）+ 补连接级消费者测试（含「v1 全量编码必须 OperationalError」防回归锁）。若未在期末抓到，桌面版在含空格用户名的机器上全部打不开数据库。

## 教训

**双端镜像契约测试必须包含真实消费者连接级用例**：

1. 契约表只钉「字符串级预期」是不够的——每个镜像端点都要有对应「消费者级」用例（真实建库、真实连接、真实读写），Python/Rust 各一份
2. 跨层/跨语言的「对齐」动作，先问双方消费者是谁：同一个 URL 字符串，SQLAlchemy 与 sqlite3 URI 的解码语义不同，不能盲目对齐
3. 防回归锁要有「反例用例」：钉住「错误形态必须失败」（本案例：v1 全量编码必须 OperationalError），否则未来有人改回 v1 测试不会红
